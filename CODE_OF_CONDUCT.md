# Code of Conduct

## Our Commitment

Smart File Manager is an open-source project built for people who want to create, learn, contribute, and share software.

We want the project community to be welcoming, respectful, constructive, and safe for everyone who participates.

This Code of Conduct explains the behavior expected from contributors, maintainers, issue reporters, pull request authors, and other community members.

By participating in the Smart File Manager community, you agree to follow this Code of Conduct.

## Expected Behavior

Community members are expected to:

* Treat other people with respect.
* Be constructive when giving feedback.
* Assume good intentions when possible.
* Communicate clearly and professionally.
* Welcome different levels of experience.
* Be patient with beginners and people learning new technologies.
* Explain technical disagreements using evidence and reasoning.
* Respect different approaches to solving technical problems.
* Keep discussions focused on the project when appropriate.
* Give credit to other people's work.
* Respect project maintainers, contributors, and users.
* Report bugs and security problems responsibly.
* Follow the project's documentation and contribution guidelines.
* Help maintain a friendly and useful development environment.

## Technical Discussions

Technical disagreements are normal in open-source development.

Different contributors may have different opinions about:

* Architecture
* User interface design
* File organization behavior
* Performance
* Dependencies
* APIs
* Documentation
* Testing
* Project structure
* Future features

Disagreements should focus on the technical subject rather than the person proposing an idea.

Good technical feedback explains:

1. What the concern is.
2. Why it matters.
3. What evidence supports the concern.
4. Possible alternatives when appropriate.

Statements such as "this implementation has a performance problem because..." are more useful than personal attacks or dismissive comments.

## Constructive Feedback

When reviewing issues, pull requests, code, documentation, or other contributions:

* Focus on the work rather than the individual.
* Explain problems clearly.
* Suggest improvements when possible.
* Avoid unnecessary hostility.
* Avoid mocking beginners or inexperienced contributors.
* Recognize useful contributions even when changes are not accepted.

Maintainers may request changes before accepting a contribution. This is part of the normal development process and should not be treated as a personal rejection.

## Unacceptable Behavior

The following behavior is not acceptable in the Smart File Manager community:

* Harassment or targeted abuse.
* Personal attacks.
* Threats of violence.
* Hate speech or discriminatory behavior.
* Deliberate intimidation.
* Repeated unwanted contact.
* Sexual harassment.
* Sharing private or sensitive information about another person without permission.
* Doxxing.
* Impersonating project maintainers or contributors.
* Deliberately disrupting project discussions.
* Trolling intended to harass or provoke others.
* Spam.
* Malicious behavior toward contributors or users.
* Deliberately submitting harmful code or changes.
* Knowingly misleading contributors about technical or security issues.
* Retaliating against someone who reports misconduct in good faith.

This list is not exhaustive. Behavior that substantially interferes with a safe and constructive project environment may also be addressed by the maintainers.

## Respecting Privacy

Do not publish or request private information about other community members.

This includes, but is not limited to:

* Home addresses
* Phone numbers
* Private email addresses
* Passwords
* Authentication credentials
* Private messages
* Personal documents
* Private account information
* Other information that was not intended for public disclosure

Public project information should remain separate from private personal information.

## Security Reports

Security vulnerabilities should not be publicly disclosed before the project has had a reasonable opportunity to investigate them.

If the repository provides a security reporting process, use the instructions in [`SECURITY.md`](SECURITY.md).

Do not use public issues to post:

* Passwords
* API keys
* Authentication tokens
* Private credentials
* Exploit details that could unnecessarily put users at risk
* Other sensitive security information

See [`SECURITY.md`](SECURITY.md) for the project's security policy.

## Issues and Bug Reports

Issues should be used to report problems, request improvements, or discuss project-related topics.

When opening an issue:

* Use a clear title.
* Provide enough information to understand the problem.
* Include reproduction steps when reporting a bug.
* Include relevant error messages or logs.
* Avoid posting private or sensitive information.
* Search existing issues when practical to avoid unnecessary duplicates.

Issues may be closed when they are duplicates, unrelated to the project, already resolved, or otherwise outside the project's scope.

## Pull Requests

Contributors are encouraged to submit pull requests that improve Smart File Manager.

Pull requests should:

* Clearly explain what was changed.
* Explain why the change is useful when appropriate.
* Keep changes reasonably focused.
* Avoid unnecessary unrelated modifications.
* Follow the project's existing coding style where practical.
* Include documentation updates when necessary.
* Avoid introducing malicious or intentionally harmful behavior.

Maintainers may request revisions, additional testing, or clarification before merging a pull request.

## Contributions From Beginners

Everyone starts somewhere.

New contributors should feel comfortable asking questions, requesting clarification, or submitting smaller changes.

Experienced contributors are encouraged to help newcomers understand the project when practical.

Mistakes are a normal part of software development. Good-faith mistakes should be treated as opportunities to learn rather than reasons for personal attacks.

## Documentation Contributions

Documentation is an important part of the project.

Contributors may improve:

* README content
* Installation instructions
* Troubleshooting information
* Usage documentation
* Examples
* Comments
* Guides
* Release notes

Documentation contributions should aim to be accurate, understandable, and consistent with the actual behavior of the software.

## Community Discussions

Project discussions should remain useful and reasonably focused.

Community members should avoid:

* Repeatedly derailing technical discussions.
* Flooding conversations with unrelated content.
* Starting arguments for the purpose of provoking others.
* Repeatedly reopening resolved arguments without new information.
* Turning technical disagreements into personal conflicts.

Friendly humor is welcome when it does not become harassment or make others uncomfortable.
